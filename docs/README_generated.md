  - 【介護領域新規SaaS】マルチフロント構成の技術選定を意図的に分離（病院向けVuetify / 施設向けTailwind + Clean Architecture / DDD寄り）。早すぎる抽象化を避けて共通化をドメイン層に限定する技術判断と、ジュニアエンジニア育成の学習ステップ設計（中間レベル → 本来到達レベルへ段階的に上げる）の両側面を兼ねた選定。Firestoreセキュリティルールにroleベースと所属ベースの二層権限モデルを実装。「やらない」判断もADRに残し、後続の議論コストを削減
  - 【介護領域SaaS管理画面】介護領域SaaSの運用管理画面（Back Office）を0→1で単独設計・初期実装。Next.js 13 + NestJS 10 + Firebase + PostgreSQL（Prisma）の3層構成（フロント / APIサーバ / Cloud Functions）を構築。フロントエンドにClean Architecture / DDDを本格適用。`I*Repository` 抽象 + Mapperパターン + Context-based DIで、将来のサーバー API化を見越した永続層分離を先制的に整備
  - 【介護領域SaaS管理画面】Firestore Security Rules（数百行規模）を「バックエンドの代替」として徹底活用。`checkFK`（NoSQLの外部キー制約相当）、スキーマ + 不変フィールド検証、ドメイン値検証をすべてルールに集約し、フロントを信用しないゼロトラスト設計を実現。`DatabaseTimestamp` 値オブジェクトラッパーでFirestore Timestamp取り扱いを安全化し、`undefined` 系の頻出ランタイムエラーを根本撲滅
  - 【介護領域SaaS管理画面】「ジュニアでも追えるClean Architecture」を設計テーマに採用。InversifyJSのような重量IoCを避けContext + newで軽量DI。UseCase層を切らずService + Repositoryの2層に圧縮、Mapper / Repositoryの境界だけは強く守る最小構成。TODO / NOTEコメントを「次に学ぶべき概念」のロードマップとしてリポジトリに埋め込み、テスト・OOP・DDD未経験のジュニア1名を次期テックリードまで育成。運用移管後も破綻なくメンテナンスが継続

## 設計思想 / Design Philosophy

### 「やらない」判断を ADR に残す

共通UIコンポーネント化、Next.js移行、OpenAPI化、UseCase層の追加など、
誘惑の多い改善案を「現時点では採用しない」として理由付きで保留にする。
技術選定は採用するものの理由よりも、却下するものの理由を残すほうが組織を育てる。
後続の議論コストを下げ、判断の経緯を組織知として継承する。

### 育成と技術選定を統合する

教育に十分なコストを掛けられない現場では、技術選定そのものを学習機会として設計する。
本来到達したいレベル（DDD / Clean Architecture）を最初から押し付けず、
中間レベルから段階的に上げる学習ステップを技術選定に組み込み、ジュニアでも追える設計に。
技術判断と育成判断を分離せず、同じ意思決定で両立させる。

### コードを教科書として書く（人にも AI にも）

Entity / IdValueObject / AbstractValueObjectの3つの基底をそろえて
クラス・抽象・継承の概念を実例で見せる。
命名・ディレクトリ・テスト構造そのものが学習教材として機能する状態に作る。
副次的に、AI（Claude Code / Cursor / Codex等）にとってもハーネスエンジニアリングが効きやすい
コードベースになり、人間とAIの双方にとって読みやすいリポジトリが実現する。

### ゼロトラスト設計（ルールが設計書として読める粒度まで）

フロント直アクセス（Firestore SDK直接利用、RDBのRLS等）を許可する代わりに、
ルール側でドメインバリデーション・外部キー制約相当・スキーマ検証を完結させる。
バックエンドを薄く保ちつつ、フロントを信用しない設計。
RLS系のアーキテクチャでは特に重要で、ルールが設計書として読める粒度まで作り込む必要がある。

### 早すぎる抽象化を避ける

現時点で必要のない共通化は明示的に保留する。
共有UIコンポーネント、汎用ORM、独自フレームワーク等は
「2つ目以降の事例が出てから抽象化する」を原則に、
代わりに共有するのはドメイン層（用語と契約）だけに限定する。
過剰な抽象化が将来の変更コストを増やすことを避ける。
